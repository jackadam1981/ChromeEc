# Zephyr AP Power Sequence Configuration

[TOC]

## Overview

In Chrome devices, one of the main features of Embedded Controller (EC) is to orchestrate
power sequences for the platform, one of the key components that are included in this task
is the Application Processor (AP).

EC monitors various digital and/or analog signals to act accordingly and drive AP power state
transitions by generating synchronized power control signals.

## Kconfig Options

The Kconfig option `AP_PWRSEQ` enables AP power sequence in to EC application. Refer to
[Kconfig] for all sub-options related to AP power sequence support.

## Devicetree Nodes

The devicetree defines all the power signals used by the AP power sequence code.
The power signals are categorized based on their function with respect to the EC.

- Electrical signals monitored by the EC are power signal inputs. This includes power
good indicators generated by board logic and status indicators generated by the AP.
- Electrical signals driven by the EC are power signal outputs. This includes signals
to enable power rails, and to signals connected to the AP that indicate when power
rails are stable.

Each power signal is associated with an [enumeration name] to be identified by AP power sequence,
and an interface that deals with electrical signal interpretation and couples AP power
sequence with the rest of the hardware in the platform. Power signal interfaces supported are:

Power Signal | Source | Devicetree node
:------ | :------ | :------
GPIO | [signal_gpio.c] | [intel,ap-pwrseq-gpio.yaml]
ADC | [signal_adc.c] | [intel,ap-pwrseq-adc.yaml]
Virtual Wire | [signal_vw.c] | [intel,ap-pwrseq-vw.yaml]

Once power signal devicetree nodes are defined, user will be able to acces its value utilizing
power signals API, see [power_signals.h].

In the following example, we will be defining a handful of power signals, each bound to
a single supported interface:

my_project.dts
```
	/* This is a GPIO output signal */
	pwr-sys-rst-l {
		compatible = "vendor,ap-pwrseq-gpio";
		enum-name = "PWR_SYS_RST";
		gpios = <&gpioc 5 (GPIO_ACTIVE_LOW|GPIO_OPEN_DRAIN)>;
		output;
	};

	/* This is an ADC input signal */
	pwr-pg-pp3300 {
		compatible = "vendor,ap-pwrseq-adc";
		enum-name = "PWR_PG_PP3300";
		trigger-high = <&pp3300_trig_high>;
		trigger-low = <&pp3300_trig_low>;
	};

	/* This is a virtual wire input signal */
	pwr-slp-s5 {
		compatible = "vendor,ap-pwrseq-vw";
		enum-name = "PWR_SLP_S5";
		virtual-wire = "ESPI_VWIRE_SIGNAL_SLP_S5";
	};
```

This C code snipped shows how power signals are accessed, note that `enum-name` property
is expanded to be part of `enum power_signal`.

```
	...
	pg_pp3300 = power_signal_get(PWR_PG_PP3300);
	slp_s5 = power_signal_get(PWR_SLP_S5);
	...
	if (pg_pp3300 || !slp_s5) {
		power_signal_set(PWR_SYS_RST, 0);
	}
```

## Board Specific Code

In some boards, a single power signal may be associated with more than one interface or
requires further logic to determine its state value, for such cases `vendor,ap-pwerseq-external`
power signal interface can be used, this interface node requires defining function
`board_power_signal_get` where all external interface signals will be handled.

Let us consider the following scenario where power signal `PWR_ALL_SYS_PWRGD` is defined for an
Intel board:

my_external_signal.dts
```
	pwr-all-sys-pwrgd {
		compatible = "intel,ap-pwrseq-external";
		enum-name = "PWR_ALL_SYS_PWRGD";
	};
```

my_external.c
```
	int board_power_signal_get(enum power_signal signal)
	{
		switch(signal) {
		/* All other external signals defined */
		...
		case PWR_ALL_SYS_PWRGD:
			pg_pp3300 = power_signal_get(PWR_PG_PP3300);
			slp_s5 = power_signal_get(PWR_SLP_S5);
			/* Required routine to determine 'result' value */
			...
			if (result && pg_pp3300 && slp_s5) {
				return 1;
			}
			return 0;
			break;
		default:
			return 0;
		}
	}
```

## Threads

When this feature is enabled, the routine `pwrseq_loop_thread` is created, the thread
stack size is set using `CONFIG_AP_PWRSEQ_STACK_SIZE`, its priority is set with
`CONFIG_AP_PWRSEQ_THREAD_PRIORITY` its value must be selected in such way thread priority is
in the middle of all the enabled threads. If `CONFIG_AP_PWRSEQ_AUTOSTART` is set, thread
will start running as soon as it is created, otherwise, function `ap_pwrseq_task_start`
must be called to initiate thread execution.

## Testing and Debugging

Intel Chrome devices include `CONFIG_X86_NON_DSX_PWRSEQ_CONSOLE`, this enables the following console
commands to query AP power state:

- `powerindebug`: Get/set power signals
- `powerinfo`: Get current AP power state

For reference see [x86_non_dsx_common_pwrseq_console.c] .
