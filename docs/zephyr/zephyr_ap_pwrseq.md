# Zephyr AP Power Sequence Configuration

## Overview

In Chrome devices, one of the main features of Embedded Controller (EC) is to orchestrate
power sequences for the platform, one of the key components that are included in this task
is the Application Processor (AP).

EC monitors various digital and/or analog signals to act accordingly and drive AP power state
transitions by generating synchronized power control signals.

## Devicetree Nodes

AP power sequence requires to have a number of power signals (PS) configured using devicetree.
To put things in context, any electrical signal that is monitored by the EC and is
used to report the current power state of the platform is know as an input PS,
on the other hand, any electrical signal generated by the EC in response to input PS
commanded by AP power sequence corresponds to an output PS.

Each PS is associated with an enumeration name to be identified by AP power sequence
and an interface that deals with electrical signal interpretation and couples AP power
sequence with the rest of the hardware in the platform. PS interfaces supported are:
GPIO, ADC & Virtual Wire.

In this example, we will be defining a handful of intel PS's, each is bound to
a single supported interface:

my_project.dts
```
	/* This is a GPIO output signal */
	pwr-sys-rst-l {
		compatible = "intel,ap-pwrseq-gpio";
		enum-name = "PWR_SYS_RST";
		gpios = <&gpioc 5 (GPIO_ACTIVE_LOW|GPIO_OPEN_DRAIN)>;
		output;
	};

	/* This is an ADC input signal */
	pwr-pg-pp3300 {
		compatible = "intel,ap-pwrseq-adc";
		enum-name = "PWR_PG_PP3300";
		trigger-high = <&pp3300_trig_high>;
		trigger-low = <&pp3300_trig_low>;
	};

	/* This is a virtual wire input signal */
	pwr-slp-s5 {
		compatible = "intel,ap-pwrseq-vw";
		enum-name = "PWR_SLP_S5";
		virtual-wire = "ESPI_VWIRE_SIGNAL_SLP_S5";
		vw-invert;
	};
```

my_project.c
```
	...
	pg_pp3300 = power_signal_get(PWR_PG_PP3300);
	slp_s5 = power_signal_get(PWR_SLP_S5);
	...
	if (pg_pp3300 && !slp_s5) {
		power_signal_set(PWR_SYS_RST, 0);
	}
```

There may be cases where a single PS is associated to more than one interface or
requires a unique way to decode its state value, for such scenario `external` PS interface
can be used. Let us consider the following scenario where PS `PWR_ALL_SYS_PWRGD` is
defined:

my_external_signal.dts
```
	pwr-all-sys-pwrgd {
		compatible = "intel,ap-pwrseq-external";
		enum-name = "PWR_ALL_SYS_PWRGD";
	};
```

Having external PS requires having function `board_power_signal_get` defined, where
signal processing will be performed:
my_external.c
```
	int board_power_signal_get(enum power_signal signal)
	{
		pg_pp3300 = power_signal_get(PWR_PG_PP3300);
		slp_s5 = power_signal_get(PWR_SLP_S5);
		/* Required routine to determine 'result' value */
		...
		if (result && pg_pp3300 && slp_s5) {
			return 1;
		}
		return 0;
	}
```

## Threads

When this feature is enabled, the routine `pwrseq_loop_thread` is created, the thread
stack size is set using `CONFIG_AP_PWRSEQ_STACK_SIZE`, its priority is set with
`K_PRIO_COOP(8)`. If `CONFIG_AP_PWRSEQ_AUTOSTART` is set, thread will start running
as soon as it is created, otherwise, function `ap_pwrseq_task_start` must be called
to initiate thread execution.
